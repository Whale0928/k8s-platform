# 2026.11.17 K3s 업그레이드 기록

## 범위와 진행 상태

Oracle Cloud arm64 서버 4대(`instance-node-1`부터 `instance-node-4`)와 Proxmox amd64 워커 2대(`pve-pod-1`, `pve-pod-2`)를 `v1.36.6+k3s1`로 통일했다. 6대 모두 Ready이며 스케줄링을 재개했다. 실제 containerd는 `2.3.7-k3s1.36`, etcd는 `3.6.14`이다. 단계마다 실행 상태·네트워크·플랫폼을 독립 검증했다.

서버 한 대씩 적용하고 API·etcd·네트워크·Pod 실행 상태를 확인한 뒤 스케줄링을 재개한다. 각 단계에서 현재 etcd 리더는 서버 중 마지막으로 적용하고 서버를 모두 마친 뒤 워커를 적용한다. 4개 etcd voter의 quorum은 3이므로 두 서버를 동시에 중지하지 않는다.

VM 재부팅, drain, 강제 eviction, killall, uninstall은 실행하지 않았다. K3s 바이너리만 공식 체크섬을 확인해 교체하고 해당 `k3s` 또는 `k3s-agent` 서비스만 재시작한다. 설정 파일·systemd unit·환경 파일·drop-in은 해시로 보존 여부를 검사한다. 작업별 Pod UID·container ID·restart count·Ready 상태를 전후 비교한다.

## 적용 경로

기존 서버와 pve-pod-1은 `v1.33.5+k3s1`, pve-pod-2는 `v1.34.3+k3s1`이었다.

1. 서버 4대만 `v1.33.7+k3s3`으로 올려 embedded etcd를 `3.5.21`에서 `3.5.26`으로 옮겼다.
2. 서버와 워커를 순서대로 `v1.34.13+k3s1`로 통일했다. 서버의 etcd는 `3.6.14`, 전체 cluster version은 `3.6`으로 전환됐다.
3. 6대를 `v1.35.10+k3s1`로 올렸다. containerd는 `2.2.10-k3s1`이다.
4. 6대를 `v1.36.6+k3s1`로 올리고 실제 containerd `2.3.7-k3s1.36`을 확인했다.

### etcd 전환 시 확인한 경계

K3s의 [1.34 업그레이드 경고](https://docs.k3s.io/release-notes-old/v1.33.X#k3s-v134-upgrade-warning)를 확인하고 서버에 중간 버전을 먼저 적용했다. 최신 upstream의 3.5.32 권고를 K3s 3.5.26이 모두 충족한다고 간주하지 않았다.

각 서버의 K3s를 중지한 동안 snapshot·WAL을 별도 보호 디렉터리에 복사했다. 공식 `etcdutl 3.5.32`로 복사본의 snapshot 5개와 WAL 5개를 검사하고 원본·복사본의 해시 및 파일 목록이 바뀌지 않았음을 확인했다. custom v2 데이터가 없다는 직접 검사 결과와 K3s의 배포 경로를 근거로 한 대씩 전환했다. 도구를 실행한 대상은 복사본이며 live data-dir에는 실행하지 않았다. 검증을 마친 임시 복사본은 파일 목록·해시를 확인하고 제거했다.

첫 3.6 서버와 혼합 버전 상태, 마지막 3.6 서버 적용 후에 기존 4개 member ID·peer IP·learner 0·단일 리더·cluster version을 다시 확인했다. 3.6 전환 뒤에는 예전 바이너리 교체를 안전한 롤백으로 취급하지 않는다.

## 네트워크 보존

- 기본 InternalIP와 flannel IPv4는 Tailscale 주소를 사용한다. `flannel-iface=tailscale0`, backend `vxlan`을 유지한다.
- MTU는 `tailscale0=1280`, `flannel.1/cni0=1230`을 유지한다.
- `ip_forward=1`과 `all/default/tailscale0/flannel.1/cni0`의 `rp_filter=2`를 유지한다.
- node-3의 Tailscale netfilter는 `on`, 나머지 5대는 `nodivert`를 유지한다. 일괄 변경하지 않는다.
- node-1의 `ts-input` UDP 8472 허용 규칙과 node-1·2의 Docker filter/NAT 체인·FORWARD 연결을 보존한다.
- pve-pod-1은 명시적인 `node-ip` 없이 `tailscale0`에서 IPv4와 IPv6를 선택한다. 기존 IPv6를 잃는 IPv4 전용 설정을 추가하지 않는다.
- node-4의 공인 ExternalIP와 SSH 접근용 NIC는 그대로 둔다. 모든 네트워크 주소를 Tailscale 주소 하나로 바꾸는 작업은 수행하지 않는다.

node-3에서 서버와 함께 실행되던 중복 `k3s-agent`는 중지·비활성화했다. node-1·2의 사용하지 않는 bootstrap 서버 주소는 기존 node-4의 Tailscale API 주소로 교체하고 인증된 TLS 연결을 확인했다.

검사는 기존 Pod에서 DNS 18건·TCP 54건·외부 HTTPS 2건과 Redis 접근 허용/차단 정책 10건을 실행한다. etcd/API/peer port와 IP·MTU·sysctl·netfilter도 별도로 검사한다. 이 검사는 모든 서비스의 업무 동작을 증명하는 테스트는 아니다.

1.36에서는 containerd 변경 전후로 기존 active Pod 각각의 CRI sandbox ID·Kubernetes PodIP·CRI IP를 비교하고 `RuntimeReady`·`NetworkReady`를 확인한다. hostNetwork Pod의 빈 CRI IP는 Kubernetes PodIP와 별도로 비교한다.

각 노드의 독립 비교를 마친 뒤 고정된 캐시 이미지를 사용하는 진단 Pod 하나로 신규 sandbox의 CNI 초기화·DNS·Kubernetes Service TCP 연결을 검사한다. 이미지 pull·Secret 마운트·서비스 계정 token·볼륨·hostNetwork·권한 상승 없이 UID 999와 읽기 전용 rootfs로 실행한다. server dry-run과 실제 생성 응답의 사양을 확인하고 완료 후 UID precondition을 붙여 삭제한다. Pod와 실행 중 sandbox가 없음을 확인하며 종료된 sandbox의 정상 GC 대기와 실행 중 잔존을 구분한다. 강제 CRI 제거는 하지 않는다.

## 플랫폼 구성 요소

| 구성 요소 | 적용 버전과 보존 사항 |
|---|---|
| Argo CD | `v3.5.7`; repo-server 2개, KSOPS custom tools와 기존 Secret 마운트 보존 |
| cert-manager | `v1.21.3`; Certificate 7개의 `rotationPolicy: Never`를 명시하고 기존 revision·CertificateRequest 29개 보존 |
| Envoy Gateway | `v1.9.3` |
| Envoy proxy | `v1.39.6`, digest `sha256:1cac8b3a2f72d5a0918f54d7b49e68aae0b0ba325c2d50c8a9a3fff7a4d1f994` 고정 |

지원 범위에 맞춰 구성 요소도 중간 버전을 순서대로 적용했다. Argo CD 4개 Application에 native hard refresh를 요청하고 새 reconciliation과 실제 repo-server의 Kustomize·KSOPS 실행 성공을 확인한다. 렌더된 Secret 원문은 출력하거나 저장하지 않는다.

Envoy의 기존 BackendLBPolicy와 XListenerSet CRD를 명시적으로 보존한다. `safe upgrades legacy patch.json`은 기존 BackendLBPolicy의 spec과 기존 bundle/channel이 같은 UPDATE에만 좁은 예외를 허용한다. 나머지 validation과 Fail/Deny를 유지했다. 실제 server dry-run admission에서 낮은 legacy bundle을 유지한 schema 설명·served 변형, bundle 1.2.2 변경·bundle 삭제, channel standard 변경 등 5건을 거부하는지 확인했다. 유효한 새 bundle은 원래 upstream의 버전 하한 정책을 따른다. 전체 정책을 비활성화하거나 버전 라벨을 위조하지 않는다.

HAProxy 2개, Gateway 리스너 7개, HTTPRoute 13개, proxy endpoint 2개를 점검한다. 실제 proxy listener에서 mandatory PROXY protocol·외부 XFF 제거·`use_remote_address=true`·`xff_num_trusted_hops=0`을 확인한다. 전용 readiness listener는 외부 Service에 노출하지 않는다.

## 데이터 서비스와 관측 범위

PostgreSQL·ClickHouse는 로컬 인증 문맥에서 `SELECT 1`을 실행한다. Redis 복제형은 master 1개·replica 2개와 link up·sync 0을 확인하고 Sentinel 3곳의 quorum을 검사한다. standalone Redis도 확인한다.

pve-pod-2는 단계 직전 기준과 최초 기준을 함께 보존하고 총 13개 실제 프로세스를 비교한다. PG의 PID·kernel start ticks·서버 시작 시각, ClickHouse의 PID·start ticks·uptime, Redis/Sentinel의 PID·uptime을 확인한다. PG의 경과 시간은 측정 시각에서 서버 시작 시각을 뺀 값이며 PG의 별도 uptime 함수 결과가 아니다.

1.34·1.35·1.36 단계에서 7개 데이터 서비스 그룹의 health와 13개 프로세스의 연속성이 통과했다. 사용자 테이블의 전체 내용·쓰기·복구·애플리케이션 업무 시나리오를 검증한 결과는 아니다.

초기 단계에서 일부 Pod의 Ready가 잠시 내려갔다가 회복했고 etcd pending이 일시적으로 0보다 큰 표본도 있었다. 실패 표본을 보존하고 재관측한 뒤 다음 노드로 진행했다. node-1 재시작 중 관리 경로의 Redis exec 검사 실패와 한 차례 source Pod exec 실패는 검사 범위가 채워지지 않은 표본이며 서비스 트래픽 장애 여부를 입증하지 않는다. 첫 1.34 node-3 이후의 일반 PROBE 실패는 당시 세부 원인을 분류하지 못했다. 이후에 붙인 진단 라벨로 과거 원인을 단정하지 않는다. 무중단을 보장하거나 증명한 작업으로 기록하지 않는다.

## 복구 자료

각 minor 단계 직전에 node-2에서 etcd 스냅샷을 만들고 스냅샷·server token·바이너리·필요한 설정을 묶어 별도 물리 호스트 `home-lap-node-2`로 중계했다. 아카이브를 Mac 디스크에 저장하지 않고 메모리 스트림으로 전송했다. 원본 7개 항목의 해시를 도착 아카이브의 항목과 대조하고 중계 스트림과 도착 아카이브 전체의 해시를 비교했으며 디렉터리 root 700·아카이브 root 600을 적용했다.

보호된 원격 보관 위치는 `/root/k3s upgrade 2026.11.17/`이다. 단계별 파일은 `before bridge`, `before 1.34`, `before 1.35`, `before 1.36` 접두사를 사용한다. 각 노드의 최초 바이너리는 `/root/k3s upgrade recovery/original k3s`에 보호해 보관한다. 인증정보와 아카이브 내용은 Git에 넣지 않는다.

etcd snapshot restore는 실제로 수행하지 않았다. 이 백업은 control-plane 복구 자료이며 PostgreSQL·ClickHouse·PVC 데이터 백업을 대신하지 않는다. 복구할 때는 대상 K3s/etcd 버전과 token을 포함한 공식 절차를 별도로 검토해야 한다.

마지막 hard refresh의 실제 렌더는 repo-server 한 개에 배정됐다. 다른 replica는 Ready와 KSOPS 설정 보존을 확인했으며 마지막 주기에서 두 replica 모두 렌더했다고 주장하지 않는다. 이전 1.35 주기에는 두 replica의 실제 실행을 확인했다.

Failed Pod 2개는 2026.10.15와 2026.11.01에 실패한 기존 MFDS 수집 Job이며 이번 업그레이드에서 새로 실패한 실행은 아니다. 임의로 삭제하지 않았다.

node-3에서는 09:33:12 UTC에 이미지 사용률 70%에서 `FreeDiskSpaceFailed` 경고가 한 번 발생했다. 첫 GC가 목표 약 4.42GB를 확보하지 못했지만 09:38:12 UTC의 다음 자동 GC에서 이미지 31개·보고 크기 4,432,191,702B를 정리한 로그와 성공 metric을 확인했다. 경고 count는 1이며 이후 재발하지 않았다. 후속 확인에서 root/imagefs 가용량은 약 20.09GiB(45.58%), inode 여유는 94.61%, DiskPressure는 false였다. 수동 image prune이나 이미지 삭제는 실행하지 않았다. 재시작 직후 이미지 기록의 최소 나이 보호가 첫 실패에 영향을 줬을 가능성은 [Kubernetes 이미지 GC 코드](https://github.com/kubernetes/kubernetes/blob/v1.36.6/pkg/kubelet/images/image_gc_manager.go#L359-L378)에 근거한 추론이며 개별 이미지의 skip 사유를 직접 관측한 결과는 아니다.

운영 도구의 로컬 fixture는 단일 노드 업그레이드 136개, CNI 검사 199개가 통과했다. 이 수치는 운영 검사 건수와 구분한다. 복구 실행·전체 업무 API·사용자 데이터 쓰기 검증은 수행하지 않았다.

검사를 마친 뒤 작업 전용 SSH API 포워드를 종료하고 로컬 listener 부재를 확인했다. 서버 4대에 올려 둔 공식 etcdctl·etcdutl 임시 바이너리 8개도 해시·소유자·미사용 상태를 확인한 뒤 제거해 135,529,792B를 회수했다. live runtime 파일과 보호된 복구 자료는 유지했다.
