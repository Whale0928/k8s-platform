# Warpgate 접근 기록 관리

## 적용 결과

2026.09.30 공용 진입점 차단과 기록 보관 정책을 적용했다.
Warpgate는 Ready 1/1, 재시작 0회, 메모리 51Mi로 복구됐다.
외부 웹 UI GET 200, PostgreSQL TLSv1.3 인증서 검증, SSH 리스너 응답을 확인했다.
기존 bottle-note.com도 HTTP 200을 유지했다. 인증정보를 사용한 실제 DB/SSH 로그인은 이번 검증에 포함하지 않았다.
치즈레이크는 요청에 따라 작업 범위에서 제외했다.

초기 정리 Job은 100초에 완료됐으며, 미인증 세션 410,142건, 로그인 실패 305,361건, 오래된 로그 461건을 삭제했다.
정상 인증/타겟 접근 세션은 적용 전후 51건으로 동일하고 누락된 세션 ID는 0개다.
검증 시 현재 세션 3,626건, 사용자 4개, 타겟 9개, 녹화 0개였다.
기본 정리와 새 접속이 계속되므로 현재 행 수는 변할 수 있다.

## IP 차단 기준과 범위

로그인 실패 451,659건과 소스 IP 3,802개를 분석해 107개 IP를 선정했다.
이 IP의 실패는 436,993건으로 전체의 96.8%다.

- 공개 IP, 로그인 실패 100건 이상, 존재하지 않는 사용자 시도 100건 이상.
- 추가 근거: 존재하지 않는 사용자 5종 이상, 흔한 탐색 계정 100건 이상, 기존 차단 로그 100건 이상 중 하나.
- 정상 인증/타겟 접근 이력이 있는 IP 2개와 내부망, loopback, link-local, Tailscale CGNAT 주소를 제외했다.
- 후보와 정상 인증 주소 및 Kubernetes 노드 IP 중복은 모두 0개다.
- 정확한 주소만 차단하며 CIDR로 확대하지 않는다. 다른 홈랩 웹서비스 이용 여부까지 확인한 목록은 아니다.

`platform/gateway/blocked_ips.lst`가 HAProxy 입력이고 `docs/2026.09.30 Warpgate IP 차단 근거.csv`에 주소별 근거가 있다.
실제 `envoy-gateway-system/edge-haproxy` 두 Pod에서 동일한 107개 목록과 설정 로드를 확인했다.
80·443·5432·2222를 통해 들어오는 홈랩 공용 서비스에 적용된다.
노드 SSH 22, Kubernetes API 6443, 직접 노출된 NodePort에는 적용되지 않는다.
고정 목록에는 자동 만료가 없다. 2026.10.30까지 재검토하고 정상 사용자 신고 시 해당 주소를 제거한다.

## 기록 보관 정책

| 기록 | 보관 기간 | 관리 방식 |
|---|---:|---|
| 정상 인증 세션과 녹화 | 30일 | Warpgate 기본 정리, log.retention 30days |
| 종료된 미인증 세션 | 1일 | 별도 유지보수 Job, 500건 단위 삭제 |
| 로그인 실패 기록 | 7일 | 유지보수 Job, 로그인 보호 retention 604800초 |
| 일반 애플리케이션 로그 | 7일 | 유지보수 Job |
| 감사 로그 | 30일 | 유지보수 Job 및 log.audit_retention 30days |

별도 유지보수는 활성 세션, 사용자/타겟 정보나 snapshot이 있는 세션, 녹화가 연결된 세션을 삭제하지 않는다.
사용자, 타겟, 자격증명, 역할, IP block, lockout 행은 유지한다.
기존 log 테이블에는 session FK가 없으므로 세션 원본을 제거한 뒤 일반 로그는 별도 7일 유지한다.
일반 로그가 7일 뒤 삭제돼도 정상 세션 메타데이터는 30일 남을 수 있다.

`warpgate-history-maintenance` CronJob을 매시 17분 Asia/Seoul로 활성화했다.
동시 실행을 금지하고, 10분 제한 및 제한된 CPU/메모리로 실행한다.
DB schema나 인덱스는 변경하지 않았다. SQLite 대량 IN 목록은 최대 500개로 제한한다.
VACUUM을 실행하지 않았으며 삭제 후 빈 페이지는 재사용된다.

## 백업과 롤백

초기 삭제 전에 같은 PVC에 일관된 SQLite 백업 및 원본 YAML을 남겼다.
백업 위치는 `/data/maintenance/2026.09.30 19.31.18/`이고 DB는 472,080,384바이트, 파일 권한은 0600이다.
백업에는 자격증명이 포함되므로 외부 전송하지 않는다.
백업과 현재 DB 모두 PRAGMA quick_check 결과가 ok였다.
이 백업은 자동 삭제하지 않는다. 복구 필요성이 사라진 뒤 별도 승인으로 처리한다.

HAProxy 롤백은 이전 Git 설정과 목록을 복원해 ArgoCD로 반영한다.
DB/설정 복구는 Warpgate와 유지보수 Job을 모두 정지한 상태에서 수행한다.
배포 원본은 ArgoCD가 추적하는 main이며 selfHeal/prune가 활성화돼 있다.

## 장애 분석과 검증

장애 당시 기동 후 약 6초 동안 프로세스 메모리가 512Mi에 도달해 CONSTRAINT_MEMCG OOM 종료가 반복됐다.
DB에 미인증 세션 413,715건과 만료 세션 약 26만 건이 있었다.
해당 버전의 기동 정리는 만료 행 전체를 읽고 전체 ID 목록으로 후속 쿼리를 만든다.
보관 정책 변경과 일괄 처리 규모를 줄인 뒤 복구됐지만, 정확한 메모리 할당 위치를 프로파일링한 것은 아니다.

- `python3 -B -m unittest discover -s platform/warpgate -p test_prune_state.py -v`: 8개 통과.
- `git diff --check`: 통과.
- HAProxy 3.2.21의 haproxy -c 검사: 로컬 및 실제 두 Pod에서 통과.
- IP 목록: 107개, 중복/정상 인증 주소/노드 주소 중복 모두 0개.
- Kustomize build 및 CronJob ConfigMap 이름 참조 검증: 통과.
- Kubernetes client/server dry-run: 통과.
- 초기 유지보수 Job: Complete 1/1, 실제 삭제 건수 확인.
- 외부 HTTP GET 및 PostgreSQL TLS/SSH 리스너: 통과.
- 실제 인증 로그인, 차단 IP에서 발생하는 외부 트래픽, 장기간 안정성은 미검증이다.
