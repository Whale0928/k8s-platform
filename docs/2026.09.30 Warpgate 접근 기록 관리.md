# Warpgate 접근 기록 관리

## 확인된 상태

2026.09.30 UTC 기준 로그인 실패 451,659건, 소스 IP 3,802개를 분석했다.
세션은 413,766건이고, 현재 활성 세션은 0건이다.
Warpgate는 기동 직후 프로세스 메모리가 512Mi에 도달해 OOMKilled가 반복된다.
대량 만료 세션을 한꺼번에 읽고 ID 전체로 후속 쿼리를 만드는 기동 정리 경로가 유력한 원인이다.
할당 위치를 직접 프로파일링한 것은 아니므로 원인 확정으로 기록하지 않는다.
치즈레이크는 요청에 따라 작업 범위에서 제외했다.

## IP 차단 후보

- 후보: 107개 정확한 IP 주소, 로그인 실패 436,993건 (96.8%).
- 기준: 공개 IP, 실패 100건 이상, 존재하지 않는 사용자에 대한 시도 100건 이상.
- 추가 근거: 존재하지 않는 사용자 5종 이상, 흔한 탐색 계정 100건 이상, 기존 IP 차단 로그 100건 이상 중 하나.
- 정상 인증 또는 타겟 접근 이력이 있는 IP 2개는 제외했다. 후보와 중복은 0개다.
- 내부망, loopback, link-local, Tailscale CGNAT 주소를 제외했다.
- 정상 웹서비스 이용 여부는 Warpgate 로그만으로 확인할 수 없다. 공유 NAT와 IP 재할당 위험이 있으므로 CIDR로 확대하지 않는다.
- `platform/gateway/blocked_ips.lst`는 HAProxy 입력 파일이다. 근거는 `docs/2026.09.30 Warpgate IP 차단 근거.csv`에 있다.
- 고정 목록에는 자동 만료가 없다. 2026.10.30까지 재검토하고 정상 사용자 신고가 있으면 해당 주소를 제거한다.

## 적용 범위

실제 공용 진입점은 `envoy-gateway-system/edge-haproxy` DaemonSet의 두 Pod다.
`public-http`, `public-https`, `postgres-tcp`, `ssh-tcp`에서 연결 초기에 source IP를 검사한다.
포트 80, 443, 5432, 2222를 통해 들어오는 홈랩 서비스 전체에 적용하는 변경안이다.
노드 SSH 22, Kubernetes API 6443, 직접 노출된 NodePort에는 적용되지 않는다.
노드 전체 방화벽 변경과 동일한 효과라고 표현하지 않는다.

## 보관 정책 변경안

| 기록 | 보관 기간 | 관리 방식 |
|---|---:|---|
| 정상 인증 세션과 녹화 | 30일 | Warpgate 기본 정리, `log.retention: 30days` |
| 종료된 미인증 세션 | 1일 | 별도 유지보수 Job, 500건 단위 삭제 |
| 로그인 실패 기록 | 7일 | 유지보수 Job, 로그인 보호 retention도 604800초 |
| 일반 애플리케이션 로그 | 7일 | 유지보수 Job |
| 감사 로그 | 30일 | 유지보수 Job 및 `log.audit_retention: 30days` |

정상 인증 정보, 타겟 snapshot, 녹화가 있는 세션 및 활성 세션은 별도 유지보수에서 삭제하지 않는다.
기존 정상 세션 51건은 이 정책으로 보존된다. 사용자, 타겟, 자격증명, 역할, IP block 및 lockout 설정은 삭제하지 않는다.
로그인 보호의 오래된 실패 기록을 제거하더라도 현재 IP block/lockout 행은 유지한다.
로그 테이블에는 session FK가 없으며, 세션 원본을 제거한 뒤에도 일반 로그를 독립적으로 7일 유지한다.
일반 로그 7일 이후에는 정상 세션 메타데이터가 30일 남아 있어도 그 세션의 상세 일반 로그는 없다.

## 적용 전 준비와 순서

1. 유지보수 스크립트는 기본이 읽기 전용 preview다. 현재 DB에 preview를 실행해 삭제 건수를 확인한다.
2. 초기 적용에서는 Warpgate DB 및 설정을 권한 0600으로 같은 PVC에 백업한다. 백업 파일에는 인증정보가 포함되므로 외부 전송하지 않는다.
3. HAProxy 후보 설정은 동일 버전 `haproxy -c`로 검증한다.
4. HAProxy 두 Pod를 한 번에 하나씩 갱신하고, 정상 진입 경로의 연결과 차단 응답을 확인한다.
5. 초기 유지보수는 `--apply --configure --backup`으로 실행한다. SQLite DB와 설정 변경 전에 백업 공간과 무결성을 확인한다.
6. Warpgate Ready 및 안정적인 메모리, 재시작 횟수를 확인한 뒤 CronJob의 `suspend`를 false로 바꾼다.

`maintenance_cronjob.yaml`은 현재 `suspend: true`인 변경안이다. 매시 17분, 동시 실행 금지, 10분 제한으로 작성했다.
SQLite writer 충돌 시 5초 내 대기하고 실패하면 Job을 실패 처리한다. 무시하거나 데이터 파일을 강제로 교체하지 않는다.
기존 SQLite 인덱스나 schema는 변경하지 않고, 대량 `IN` 목록은 최대 500개로 제한한다.
VACUUM을 실행하지 않는다. 삭제 후 DB 파일 크기는 그대로일 수 있지만 빈 페이지는 재사용된다.

## 롤백

HAProxy는 이전 ConfigMap과 DaemonSet template을 복구한다.
DB/설정 복구는 Warpgate와 유지보수 Job이 모두 정지한 상태에서만 수행해야 한다.
GitOps가 selfHeal/prune 상태이므로 live patch만으로 영구 적용하지 않는다. commit/push는 별도 승인 대상이다.

## 현재 완료 범위

IP 근거 목록, 공용 진입점 차단 설정, 유지보수 스크립트와 정지 상태의 CronJob을 로컬에 준비했다.
실제 차단, DB 삭제, 보관 설정 변경, 배포와 Git 쓰기는 아직 실행하지 않았다.

## 검증 결과

- `python3 -B -m unittest discover -s platform/warpgate -p test_prune_state.py -v`: 8개 통과.
- `git diff --check`: 통과.
- 정확한 IP 107개, 중복 0개, 정상 인증 이력 주소와 중복 0개, 공개 주소 여부 검증 통과.
- 실제 DB의 스크립트 `--configure` preview: 세션 409,990건, 로그인 실패 305,201건, 로그 637건이 정리 대상이었다. 시간 기준이 움직이므로 적용 직전에 다시 확인한다.
- 동일 HAProxy 3.2.21 이미지의 `haproxy -c`로 파일 기반 목록을 포함한 설정 검증 통과. 로컬에는 클러스터 DNS가 없어 backend DNS 안내 메시지가 발생했다.
- 실제 HAProxy 두 Pod에서 동일 IP 목록을 여러 ACL 행으로 전달한 읽기 전용 `haproxy -c`도 통과했다. 현재 설정을 reload한 것은 아니다.
- Gateway Kustomize build, 유지보수 CronJob 및 script ConfigMap의 이름 참조 검증 통과.
- CronJob Kubernetes client/server dry-run 통과. 실제 CronJob은 생성하지 않았다.
- 진단 Pod 삭제 완료. 기존 워크로드, HAProxy 정책과 Warpgate 원본 데이터는 변경하지 않았다.
- 현재 체크아웃은 다른 기능의 `feat/preview-imageupdater-mapping` 브랜치다. 배포 원본은 ArgoCD가 추적하는 `main`이므로, GitOps 반영은 작업 전용 브랜치에서 이 변경만 옮겨 수행해야 한다.
