# Warpgate 접근 차단 재검토

2026.09.30에 적용한 고정 IP 차단 목록과 기록 보관 정책을 2026.10.28에 재검토했다.
Warpgate SQLite를 읽기 전용으로 마운트한 임시 Pod에서 조회했고, 조회 후 Pod는 삭제했다.

## 검토 결과

- 고정 목록 107개는 두 HAProxy Pod에 동일하게 로드돼 있고, 최근 7일간 해당 IP의 로그인 실패는 0건이다.
- 정상 인증 세션은 전부 `58.150.17.102`와 `1.227.241.137`에서 `cheese-lake`, `admin` 계정으로 접속한 PostgreSQL이며, 차단 목록 및 신규 후보와 겹치지 않는다. 두 IP의 로그인 실패도 0건이다.
- 최근 7일 로그인 실패는 78,192건(하루 약 11,200건)으로 차단 전 하루 평균(약 11,300건)과 같다. 소스 IP 312개 중 47개가 98%(76,584건)를 차지하며 모두 신규 IP다.
- 실패의 99.8%가 SSH이고 시도 계정의 96%가 `root`다. 최근 8일간 공개 SSH(2222)로 성공한 정상 세션은 없다.
- Warpgate 자체 로그인 보호는 5개 IP를 24시간 차단 중이지만, 연결 자체는 HAProxy를 통과해 Warpgate까지 도달한다.
- Warpgate Pod는 정상(Ready 1/1)이고, 10.22 재시작은 `pve-pod-2` 노드 재기동에 따른 것이다. 유지보수 CronJob은 매시 정상 완료되며 DB 행 수는 보관 정책 범위 안에 있다.
- AWS IP(`35.161.89.114`, `54.212.233.107`)에서 `cheese-lake#cheese-lake` 형식의 올바른 사용자#타겟 명명으로 PostgreSQL 인증에 실패한 기록이 있다. 무작위 스캐너보다는 잘못된 자격증명을 가진 연동 서비스로 보이며 별도 확인이 필요하다.

## 결정

고정 목록은 그대로 유지하고 신규 후보 47개는 추가하지 않는다. 공격자가 IP를 바꾸므로 고정 목록 확장은 효과가 없다.

### 공개 SSH(2222) 종료

Warpgate에 등록된 타겟은 PostgreSQL 2개와 HTTP 5개뿐이고 SSH 타겟은 없다. 감사 로그 30일과 세션 기록에 SSH 인증 성공은 0건이며, 로컬 `~/.ssh/config`, 옵시디언 운영 가이드, GitHub 코드 검색(본인 계정과 bottle-note 조직)에서도 이 리스너를 쓰는 곳이 없다. 실패의 99.8%가 이 포트로 들어오므로 HAProxy `ssh-tcp` frontend와 Service 포트를 제거한다. Warpgate 컨테이너의 2222 리스너는 Pod 안에서만 수신하며, SSH 타겟이 필요해지면 타겟 등록과 함께 다시 연다. OCI 서브넷 Security List의 2222 규칙은 콘솔에서 별도로 제거해야 한다.

### PostgreSQL(5432) 연결 빈도 자동 차단

HAProxy stick-table로 소스 IP별 연결 빈도를 추적해 5432에서 자동 차단한다.

| 포트 | 임계치 | 근거 |
|---|---:|---|
| 5432 (PostgreSQL) | 분당 40회 초과 | 정상 클라이언트 실측 최대는 분당 8회(10분 21회)이고, 스캐너는 분당 30~150회다. |

임계치를 넘긴 IP는 `gpc0` 플래그로 표시해 마지막 연결 시도로부터 1시간 동안 차단한다. 계속 시도하면 차단이 연장된다.
80·443에는 적용하지 않는다. NAT 뒤의 다수 사용자가 같은 IP로 접속하기 때문이다.
두 HAProxy 인스턴스는 테이블을 공유하지 않으므로 DNS round-robin 기준 실제 허용량은 최대 2배가 될 수 있다. 재배포 시 테이블은 초기화된다.
임계치 미만으로 느리게 시도하는 소스는 Warpgate 로그인 보호(5회 실패 시 24시간 차단)에 맡긴다.

## 검증

- HAProxy 3.2.21 운영 이미지의 `haproxy -c`: 통과(DNS 미해석 NOTICE만 출력).
- 운영 이미지로 로컬 기능 테스트(임계치 10으로 축소): 11번째 연결부터 거부되고, 70초 뒤 단일 연결도 `gpc0` 플래그로 계속 거부됨을 확인했다.
- HAProxy 3.2 매뉴얼에서 `track-sc0`, `sc-inc-gpc0`가 `tcp-request connection`에서 사용 가능함을 확인했다.
- `kustomize build platform/gateway`, `kustomize build platform/warpgate` 및 `kubectl apply --dry-run=server`: 통과.
- `git diff --check`: 통과.
- 운영 반영 후 정상 클라이언트 영향, 차단 동작, 2222 외부 접속 거부는 미검증이다.

## 롤백

`platform/gateway/haproxy.cfg`에서 `st_warpgate_src` 테이블과 `postgres-tcp` frontend의 `track-sc0`, `sc0_*` 네 줄을 제거해 ArgoCD로 반영한다.
SSH를 되돌리려면 `ssh-tcp` frontend와 `warpgate-ssh` backend, Service의 2222 포트를 이 커밋 이전 내용으로 복원한다.
ConfigMap 이름이 바뀌면서 DaemonSet이 롤링 업데이트(maxUnavailable 1)된다.
